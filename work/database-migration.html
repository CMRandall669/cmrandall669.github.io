MariaDB → MySQL migration — across two production applications

Owning the entire developer-side surface of a database platform migration spanning app config, deployment secrets, database logic, and ETL.

Role: Sole internal developer, in coordination with the DBA and BA teams.   Scope: two production applications.   Stack: MariaDB → MySQL, .NET, OpenShift, stored procedures, SSIS.

Context

Two production applications — a fleet-visibility system and an integration-monitoring platform — ran on MariaDB and needed to move to MySQL. The change wasn’t isolated to the database engine; it rippled through every layer that touches data.

Problem

A platform migration like this is deceptively broad. Beyond the database itself, MariaDB and MySQL differ in ways that affect connection configuration, deployment secrets, database-side logic, and ETL packages. Any surface left unconverted means a broken environment — and the work spanned two applications across every deployment stage.

Approach

  • Repointed .NET connection strings and updated OpenShift secrets so every environment — Dev, QA, and Production — connected to MySQL with correct, consistent configuration.
  • Adapted stored procedures for MySQL syntax and behavior differences, and modified SSIS packages so existing ETL flows continued to run against the new engine.
  • Worked alongside the DBA and BA teams on data and validation while owning the full developer-side surface across both applications.

Impact

migrated from MariaDB to MySQL
4 layers
converted: config, secrets, stored procs, ETL
Dev → Prod
configuration consistency preserved end to end
Sole dev
owning the developer-side surface of the migration

This is the kind of cross-cutting change where breadth is the whole job: the value was in covering every developer-side surface across two applications so nothing regressed when the engine changed underneath them.
