Customer Health real-time integration monitoring

Re-architecting a per-customer health dashboard from a client-side bottleneck into a server-side, near-real-time monitoring system.

Role: Sole developer, end to end data model, background service, API, and front end.   Scale: ~350 monitored customer integrations.   Stack: MariaDB, .NET 6, RabbitMQ, REST, React / TypeScript.

Context

An internal enterprise dashboard that gives operations a single place to see the health of every customer integration across several signals edge-to-edge alerts, RabbitMQ queue statistics, transaction results, and directory-monitor status each rolled up into an overall Stable / At-Risk / Critical state.

Problem

The original page computed everything in the browser. For each customer it fired a separate API call per signal, waited for all of them to return, then ran aggregation and status-calculation logic client-side before anything could render. Across ~350 customers this meant heavy request fan-out, slow and inconsistent load times, and status logic trapped in the UI where it was hard to reason about, reuse, or change.

Approach

  • Moved the entire aggregation pipeline off the front end into a .NET 6 background service (Entity Framework Core) that runs on a 5-minute cycle: it syncs the customer list, pulls each health signal, evaluates results against configured thresholds, and writes a rolled-up status to a precomputed table.
  • Designed a two-tier threshold-configuration system global defaults with per-customer overrides replacing a global-only model, plus an admin UI (inline grid editing) so operations can tune alerting without code changes.
  • Rebuilt the React / TypeScript front end (Material-UI, TanStack Query with caching, Zustand) to read a single precomputed dataset a filterable, paginated summary with export, plus accordion drill-downs and a health-gauge detail view.

Impact

~350
customer integrations monitored from one dashboard
5 min
refresh cycle near-real-time, precomputed server-side
N → 1
per-customer API fan-out replaced by a single read
Self-serve
ops adjust thresholds without a code change or deploy

Status logic now lives in one place on the server rather than scattered through the UI, making it consistent, testable, and far easier to extend as new health signals are added.
