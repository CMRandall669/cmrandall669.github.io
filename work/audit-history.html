Audit-history pattern — one design, every entity

A standardized write-time snapshot pattern that gives every configuration entity consistent, immutable, per-record change history — designed once, applied across ~9 entities.

Role: Designed the pattern and applied it uniformly across the dashboard’s configuration entities.   Stack: C# / .NET, EF Core, MariaDB, React / TypeScript.

Context

The dashboard has many configuration entities — directory monitors, message-queue file-writes, customer lists and cross-references, alert-email settings, transaction and transload configs, and more. Operations needed to see who changed what, and when, for every one of them.

Problem

Change history could have been solved ad hoc, one entity at a time — leaving ~9 slightly different implementations to maintain — or pushed into database triggers, which hide the logic in the database where it’s hard to reason about, test, or evolve. Neither approach scales as entities are added.

Approach

  • Chose an explicit, service-layer snapshot pattern over triggers or ORM interceptors: after every create, update, or delete, the service persists the live change and then snapshots the affected rows into a paired history table — keeping the logic visible, testable, and in one place.
  • Made every entity follow an identical shape — all source columns mirrored, plus AuditId, LastUpdatedAt, and LastModifiedBy — written to append-only tables that are never updated or deleted.
  • Surfaced the history where it’s needed: each entity’s details page shows the record’s current values alongside an accordion of every prior version — who changed it and when — backed by a typed React Query fetch. The same design is replicated per entity, always scoped to that entity’s own records.
  • Wrote a documented recipe so any developer can extend the same pattern to a new entity in a known, low-risk set of steps.

Impact

~9 entities
on one identical, predictable pattern
Append-only
immutable history — nothing overwritten or lost
Per record
current values plus every prior version, by whom and when
Documented
a repeatable recipe to extend it to new entities

The win isn’t any single audit table — it’s that the pattern is uniform and self-documenting. Change traceability is consistent everywhere, and adding a new entity is a known procedure rather than a fresh design problem. Standardization over cleverness.
