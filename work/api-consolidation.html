Transaction API consolidation — two verbose endpoints into one

Replacing two parallel ~1,500-line transaction endpoints with a single direction-parameterized API roughly 90% smaller.

Role: Sole developer.   Change: ~3,000 lines of duplicated code → ~250 in one shared path.   Stack: C# / .NET, REST, MariaDB.

Context

The application serves transaction data for customer integrations in two directions — inbound and outbound. Retrieval was handled by two entirely separate API endpoints, one per direction, each reading from its own set of tables.

Problem

Each endpoint was ~1,500+ lines, highly verbose, and largely a duplicate of the other — the same aggregation and shaping logic, pointed at different tables. Two code paths meant every change had to be made twice, every bug could hide in two places, and diagnosing a bad result meant reading through a wall of near-identical code.

Approach

  • Recognized that the two endpoints differed almost entirely in which direction and tables they targeted, not in their underlying logic — the duplication was structural, not essential.
  • Rebuilt the feature as a single endpoint that accepts a direction parameter (Inbound, Outbound, or Both), sharing one code path and returning the same result sets as before.
  • Added a combined result the previous design couldn’t produce — inbound and outbound together — as a natural consequence of the unified path.
  • Collapsed ~3,000 lines of verbose, duplicated code into ~250, cutting the surface area a bug can hide in and making the feature legible at a glance.

Impact

~90%
less code to read, change, and maintain
2 → 1
endpoints — a single code path, not two
+ Combined
new inbound-plus-outbound result, previously unavailable
1 place
to fix a bug or make a change, instead of two

The consolidation traded a large, duplicated codebase for a small, parameterized one — less to maintain, easier to diagnose, and more capable than what it replaced.
